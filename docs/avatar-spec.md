# Avatar package spec (for external creators)

Avatar/sound assets are produced outside the pet-app team. This document is
what to hand a creator (or follow yourself when building the dev dummy
avatar) so the package works with `AvatarLoader`/`AvatarImportValidator`
without back-and-forth. The manifest schema itself is normative in the
`protocol` repo (section 6); this doc adds the parts specific to how pet-app
actually loads sprite clips.

**2026-07-29: switched from 3D usdz to 2D sprites (PNG).** Everything below
describes the current `type: "sprites"` spec. The old usdz/RealityKit/Mixamo
pipeline this doc used to describe is retired — `usdz`/`video` avatar types
still exist as interfaces (`AvatarPlayable`), but get no further development;
if you're producing new avatar assets, make PNGs.

## Only a base image is required

Earlier, `idle` and `walk` were both mandatory. As of the 2D switch, **only
`idle` is required** — everything else, including `walk`, falls back to it.
This means a creator can ship a single illustration and the pet fully works;
additional clips are pure upside, not a blocker.

```
Avatars/{name}/
├── manifest.json
├── idle.png
├── walk.png
├── climb.png
├── fall.png
├── land.png
├── point.png
├── type.png
├── listen.png
├── react_click.png
├── react_drag.png
├── kick.png            (F12 ball-toy interaction, optional)
└── sounds/
    ├── footstep.wav
    ├── point.wav
    ├── boop.wav
    ├── kick.wav
    ├── launch.wav
    ├── ding.wav
    ├── buzz.wav
    └── listen.wav
```

A manifest clip entry `"walk": "walk"` means: load `walk.png` from this same
directory and show it. The `emotions` table (optional) works identically —
its values are also file stems, used for socket-event-driven expression
swaps instead of FSM-state clips.

## Per-file requirements

- **Format:** PNG with a transparent (alpha) background.
- **Resolution:** ~1024px tall as a guideline — comfortable headroom for
  Retina displays without being wasteful. `manifest.json`'s `scale` field
  (multiplier on top of `hitbox`) is the correction knob if a source image
  doesn't match this.
- **Proportions:** SD/chibi (roughly 2-3 heads tall) is recommended, not
  required. pet-app applies a code-driven squash-and-stretch "bounce" motion
  (idle breathing, walk bounce, land squash-recover, kick anticipation-
  stretch — see `BouncePreset.swift`) that reads best on that proportion.
  Other proportions still work; consider a lower `bounce_intensity` if the
  motion looks exaggerated on a more realistic figure.
- **Consistent anchor point:** if you're drawing more than one clip, keep the
  character's grounding point (typically the feet) at the same relative
  position in every image's canvas. Otherwise the pet visibly jumps when a
  clip switches.
- **Size budget:** ~500KB per PNG as a guideline. A flat-color illustration
  at the recommended resolution lands well under this; the budget mostly
  guards against accidentally shipping an oversized, uncompressed export.

## What the import validator checks (and what it doesn't)

`AvatarImportValidator` checks: manifest schema/version, required clips
present in the manifest, and that each required/recommended clip's
`{name}.png` file actually exists on disk and is under the size budget
(the same check, still keyed off `AvatarLoader.requiredClips`/
`recommendedClips`, now looks for `.png` when `manifest.json`'s `type` is
`sprites` instead of `.usdz`). It reports missing/oversized files so a bad
package is rejected with a clear reason instead of loading partially broken.

It does **not** check image dimensions, aspect ratio, or anchor-point
consistency across clips — those are visual-review concerns for whoever
approves a submitted package, not something worth automating for a handful
of PNGs per avatar.

## Dev dummy avatar

`Shaydi/Resources/Avatars/dummy/` ships a placeholder set (`idle`, `walk`,
`fall`, `land`, `react_click`, `kick`) generated by a throwaway script — a
simple round chibi-blob mascot, not real illustration. It exists to prove the
pipeline (manifest → PNG load → bounce motion → click-through hitbox) works
end to end before real art arrives; see that directory's own README for
specifics.
