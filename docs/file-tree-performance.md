## 제외 패턴 (`DEFAULT_IGNORES`, `src/main/file-service.ts`)

기존: `.git`, `node_modules`, `dist`, `dist-main`, `release`.

이번에 다음을 추가했다 -- 이 에디터가 구문 강조를 지원하는 언어(`languageFor()`: ts/js/json/md/css
/html/py/rs/swift/sh/yml)의 표준 빌드 산출물·의존성·캐시 디렉터리 기준이다:

| 추가 | 근거 |
|---|---|
| `.next` | Next.js 빌드 산출물 |
| `build` | 범용 빌드 출력 관례(CRA, Android/Gradle 등) -- `dist`/`release`처럼 기존에도 일반명을 포함하고 있어 일관성 유지 |
| `target` | Rust(cargo) 빌드 산출물 |
| `.venv`, `venv`, `__pycache__`, `.pytest_cache` | Python 가상환경/바이트코드 캐시/테스트 캐시 |
| `.cache`, `coverage`, `.turbo` | 범용 빌드 도구·테스트 커버리지·모노레포(Turborepo) 캐시 |
| `Pods`, `.build`, `DerivedData` | Swift/iOS(CocoaPods, SwiftPM, Xcode) 빌드 산출물 |

**의도적으로 추가하지 않은 것:** `out`처럼 빌드 산출물 관례로도 쓰이지만 손으로 짠 소스 디렉터리
이름으로도 흔히 쓰이는 이름은, 사용자 파일을 조용히 숨기는 쪽의 위험이 더 크다고 판단해 이번에는
포함하지 않았다. 실제로 문제가 되면(대형 프로젝트에서 `out/`이 늘 빌드 산출물로만 쓰인다는 게
확인되면) 추가를 검토한다.

`DEFAULT_IGNORES`는 `listTree()`(디렉터리 순회)와 `startWatching()`(chokidar 파일 변경 감시) 양쪽에
같은 Set을 쓴다 -- 트리에서 숨긴 디렉터리를 감시까지 계속하면 대형 디렉터리 안의 변경마다 이벤트를
만들어내는 낭비가 남기 때문이다. 검증: `src/main/file-service-large-tree.test.ts`의 "DEFAULT_IGNORES에
포함된 대형 디렉터리는 listTree/watch 양쪽에서 제외된다".

## 성능 실측

`scripts/benchmark-file-tree.mjs`로 로컬에서 측정한 결과다(Windows, 개발 머신 1대 기준 -- 절대적인
수치보다 "제외 패턴이 있고 없고의 배율"을 참고할 것. 실행 환경마다 절대 시간은 다르다):

| 소스 파일 수 | node_modules 파일 수(3배 규모로 가정) | 제외 적용 | 제외 미적용 | 배율 |
|---|---|---|---|---|
| 2,000 | 6,000 | 1.2초 | 4.6초 | 3.9배 |
| 20,000 | 60,000 | 6.7초 | 36.2초 | 5.4배 |

재현: `node scripts/benchmark-file-tree.mjs [소스 파일 수]` (기본값 20,000). vitest 회귀 테스트
(`file-service-large-tree.test.ts`)는 CI 러너 성능 편차를 고려해 느슨한 상한(10초/2,000여 개 파일)만
지키는 회귀 방지용이고, 실제 배율/체감 수치는 이 스크립트로 로컬에서 재는 게 정확하다.

## 현재 방식이 감당 가능한 규모

- **제외 패턴이 잘 맞는 일반적인 프로젝트(소스 파일 수천~1만 개대)**: 위 실측대로 수 초 안에
  끝난다. `listTree()`가 IPC/WebSocket 요청-응답 한 번으로 전체 트리를 돌려주는 현재 구조(W1 완료
  기준)로 충분히 감당된다.
- **소스 파일 자체가 수만 개를 넘는 초대형 모노레포**: `readDirectory()`가 디렉터리마다 `lstat` 등
  I/O를 순차적으로(형제 디렉터리는 `Promise.all`로 안 묶고 `for...of`로) 수행하므로 파일 수에
  선형 이상으로 시간이 늘어난다. 수 초를 넘어 수십 초대로 갈 수 있다 -- 이 지점부터는 "요청 한 번에
  전체 트리"라는 현재 모델 자체가 부담이 된다.

## 상한을 넘었을 때의 대응 방향 (지금 구현하지 않음, 방향만 정리)

새 정책을 크게 재설계하지 않는 선에서, 필요해지면 다음 순서로 검토할 것을 제안한다:

1. **트리 응답에 파일 수 상한/시간 제한을 걸고 UI에 경고를 보여준다** -- 가장 단순한 완화책.
   `listTree()`가 일정 개수(예: 20,000개)를 넘으면 나머지는 자르고 "제외 패턴을 늘리거나 하위
   폴더만 여세요" 같은 안내를 반환.
2. **디렉터리 단위 lazy loading** -- FileTree UI가 최상위만 먼저 받고, 사용자가 폴더를 펼칠 때마다
   그 디렉터리만 조회하는 방식으로 바꾼다. `EditorGateway`의 `file:list-tree` 요청에 `path` 파라미터를
   추가하고 `FileService.readDirectory(directory)`를 그 경로부터 시작하도록 노출하면 되므로, 지금
   구조에서 API 확장만으로 가능하다 -- 다만 렌더러(`FileTree.tsx`)가 트리를 통째로 받는 걸 전제로
   짜여 있어 상태 관리 변경이 함께 필요하다.
3. **병렬 I/O** -- `readDirectory()`의 형제 항목 처리를 `Promise.all`로 바꿔 디스크/OS 캐시가 감당하는
   한 순회 자체를 더 빠르게 만든다. 다만 이건 상수 배율 개선이라 근본적으로 트리 크기에 선형인 문제를
   없애지는 못한다 -- 위 1, 2번과 함께 볼 것.

지금 사용자층(1인 프로젝트 규모의 경량 에디터, plan/03_workspace.md 범위)에서는 제외 패턴만으로도
충분하다고 보고, 위 대응책은 실제로 수만 개 규모의 프로젝트를 여는 사례가 나오면 그때 순서대로
검토한다.
