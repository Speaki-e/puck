# pet-app directory structure draft

This document designs the pet-app repo's source tree based on
`plan/02_pet-app.md` (Team 1: 강상우 · 박해영's plan), `plan/01_protocol.md`,
and `plan/프로젝트_개요.md`. The actual code is filled in by 강상우 · 박해영
(and delegated agents) following the P0-P9 implementation order
(02_pet-app.md section 2).

## 0. Design principles

- **`project.yml` (xcodegen) is the single source of truth for the Xcode
  project.** Both `PetAgent.xcodeproj` and `PetAgent/Resources/Info.plist` are
  generated by `xcodegen generate` and are not committed (`.gitignore`).
  `project.pbxproj` is technically text, but it's a format that's practically
  hard for humans to diff/merge, so we chose an approach that avoids the
  "Xcode project file conflicts" 02_pet-app.md's collaboration rules (section 5)
  worry about, rather than mitigating it after the fact. To change
  targets/groups/build settings, edit `project.yml` and re-run
  `xcodegen generate`.
- **Top-level groups split by feature (F1-F11), not by layer.** Instead of
  MVVM's Model/View/ViewModel, folder boundaries follow 02_pet-app.md's
  feature units directly: Overlay/Avatar/Movement/WindowSensing/... . 강상우
  and 박해영 should each be able to finish most of their work inside their
  own feature folder, which also minimizes source-level conflicts.
- **The FSM is one protocol + one file per state.** `Movement/StateHandler.swift`
  (protocol) + `Movement/States/*State.swift` (12 implementations) map 1:1 to
  the 12 states in the state transition table in 02_pet-app.md section 3
  (Idle/Walk/Climb/WalkOnTop/Fall/Land/MoveTo/Point/Type/Listen/ReactClick/ReactDrag).
- **The socket contract is isolated in `Bridge/`.** Since the `protocol` repo
  is the single source of truth, `Bridge/BridgeMessages.swift`'s file header
  states explicitly that it's a manually-synced copy of
  `protocol/swift/BridgeMessages.swift`. Any change to this file must always
  be paired with a protocol-repo schema-change PR.
- **Avatar types are hidden behind the `AvatarPlayable` protocol.** The FSM
  (`CharacterController`) only knows `AvatarPlayable` — it has no idea whether
  `USDZAvatar`/`VideoAvatar`/`SpriteAvatar` is actually playing
  (02_pet-app.md F2). `VideoAvatar`/`SpriteAvatar` are out of first-pass scope,
  so they're kept as interface-only stubs for now.
- **The tool executor is one file per tool.** `Tools/Handlers/` maps 1:1 to
  the 8 pet-app-owned tools in the protocol repo's section 4 "tool registry" table
  (launch_app, list_running_apps, get_frontmost_window, find_ui_element,
  point_at, click_element, run_shell, run_applescript). When a new tool is
  added to protocol, adding one file here is the basic unit of change.

## 2. Folder details

| Folder | Feature code | Owner | 02_pet-app.md section | Notes |
|---|---|---|---|---|
| `App/` | Shared | 강상우/박해영 | section 4 (lifecycle: AppKit, LSUIElement) | Coordinates the app-launch init order here: permission self-check -> Overlay -> BridgeServer -> GlobalHotkeyManager |
| `Overlay/` | F1 | 강상우 | section 3 F1 | Experiment point for the 4-step alpha-halo mitigation procedure (`PetARView`), click-through hitbox toggle (`ClickThroughController`) |
| `Avatar/` | F2 | 강상우 | section 3 F2 | `AvatarPlayable` is the sole boundary between the FSM and concrete implementations. `VideoAvatar`/`SpriteAvatar` are interface-only |
| `Movement/` | F3 | 박해영 | section 3 F3 | `States/` maps 1:1 to the state transition table (Idle->Walk->Climb->WalkOnTop->Fall->Land, MoveTo->Point/Idle, etc.) |
| `WindowSensing/` | F4 | 박해영 | section 3 F4 | Keeps level 1 (`WindowListWatcher`, `LandingSurfaceResolver`) and level 2 (`AccessibilityPermission`, `UIElementInspector`, `ScreenCaptureFallback`) separated |
| `Audio/` | F5 | 강상우 | section 3 F5 | The core piece is `SoundTable`, which looks up FSM state names and socket event names in the same key space |
| `Input/` | F6 | 박해영 | section 3 F6 | Global hotkeys (`GlobalHotkeyManager`) and the text-input bubble (`TextInputBubbleWindow`) are separate files — only the latter is `canBecomeKey` |
| `Voice/` | F7 | 박해영 | section 3 F7 | `VoiceInputController` is the single class that owns both the PTT key event and the recording lifecycle (a design requirement) |
| `Pointing/` | F10 | 박해영 | section 3 F10 | `SyntheticClick` only executes assuming the approval gate has already passed (approval itself is the agent core's responsibility) |
| `Tools/` | F11 | 박해영 | section 3 F11, protocol section 4 | `Handlers/` maps 1:1 to the tool registry table. Adding one file is the basic unit of change when a new tool is added |
| `Bridge/` | socket server | 박해영 | section 3 F11, protocol 2·section 3 | `BridgeMessages.swift` is a manually-synced copy of the protocol repo's schema — both repos must be updated together |
| `Settings/` | Shared | 강상우/박해영 | section 4 (settings UI: SwiftUI) | The overlay itself stays pure AppKit; only the settings screen is embedded via `NSHostingView` |
| `Diagnostics/` | Shared | 강상우/박해영 | section 6 risk (CGEvent tap permission reset) | Startup permission self-check + re-prompt UI is where this risk mitigation is implemented |
| `Resources/Avatars/dummy/` | F2 | 강상우 | "아바타 리소스 소비" (Avatar Resource Consumption) section | Minimal assets for the M-A milestone (standalone, no socket). Real usdz/wav to be added later via Git LFS |
| `PetAgentTests/` | Tests | 강상우/박해영 | — | Prioritizes pure-logic coverage first: coordinate transforms, manifest parsing, FSM transitions, socket message Codable |

## 3. Not yet there / next steps

- **`.xcodeproj` is not committed.** After editing `project.yml`, running
  `xcodegen generate` (after `brew install xcodegen`) regenerates
  `PetAgent.xcodeproj` and `PetAgent/Resources/Info.plist`. All target/group
  additions and build-setting changes go through a `project.yml` PR — the
  concern the collaboration rules (02_pet-app.md section 5: "structural-change PRs
  merge immediately") were guarding against has moved from the project file
  itself to a short `project.yml` diff.
- **Logic is being implemented in order.** Every `.swift` file starts with a
  file-header comment (owner/feature code/one-line description), and gets
  filled in following 02_pet-app.md section 2's P0-P9 order (reordered so that
  modules not dependent on rendering come first — see the table in section 4).
- **Git LFS setup still needed.** `.gitattributes` already has tracking rules
  for `*.usdz`, `*.wav`, `*.mp3`, `*.m4a`, but actually running
  `git lfs install` and adding the LFS assets happens once 강상우 adds the
  dummy avatar's real assets.
- **Waiting on the `protocol` repo to be finalized.** The fields in
  `Bridge/BridgeMessages.swift` and `Avatar/AvatarManifest.swift` reflect the
  draft schema written in `plan/01_protocol.md`. Once the "week-1 all-hands
  agreements" in `프로젝트_개요.md` section 4 (finalizing the socket schema and
  manifest schema) are done, these need to be cross-checked against the
  protocol repo's actual files again.
